What the data shows
The entity exists (in the full export only). plants.nt has wfo-3400008664 = Taraxacum sect. Ruderalia (Kirschner, H.Øllg. & Štěpánek), WFO rank section, status Unchecked. The full export creates an entity for every non-synonym WFO record, so sections get entities too. It carries identity + BHL facts (25 books mention it — that works, BHL genuinely indexes that string) but no nlOccurrenceCount, firstObservationYear, nlStatus or regions.
The observations come in under a different name. gbif_nl.py downloads NL occurrences grouped by GBIF's accepted species key (specieskey, species, specieskey IS NOT NULL). I grepped the raw download plant_data/gbif_nl/0018549-261023074918325.csv: the string "ruderalia" appears zero times. Every dandelion aggregate record arrives as specieskey 54VX8 / Taraxacum officinale. So no observation name-key for the section ever reaches nl_totals — and per export decision 1, observation facts hang only on the entity matching the downloaded name.
Why the names differ: Waarneming.nl/FLORON record dandelions as the aggregate sect. Ruderalia; GBIF's backbone instead folds that aggregate into the species T. officinale (it keeps a separate, accepted Taraxacum ruderalia sp. that NL records were not mapped to). Two checklists, two concepts for "the common dandelion". plant_index even shows gbif_id = NULL for the WFO section — no crosslink exists in our data between the WFO section and any GBIF taxon.
So it's not a lost year
firstObservationYear is absent because this entity has zero observations attributed to that name, not because the years were dropped. The data is faithful: we never attribute observations to a name the source didn't record them under. The same pattern will hit every aggregate-genus concept: Rubus, Hieracium, Potentilla…
What we could do about it (pick a direction)
Leave the data as-is (my recommendation). Honest to the sources. The app can handle the UX: an entity with identity + books but no observations displays "no NL observations recorded under this name" and can deep-link to T. officinale. Zero risk of inventing taxonomic claims.
Add an explicit, documented bridge predicate — e.g. plantdb:observationsRecordedUnder <wfo-0000062154> on aggregate entities, built from a small hand-maintained mapping (Ruderalia→officinale, a handful of NL aggregates). Reads perfectly in a query, but we'd be asserting a FLORON convention the checklists don't endorse — needs to be labelled as exactly that.
Suppress infrageneric entities from the entity list (species/infraspecific + name keys only). Cleaner search results, but we'd lose the legit 25-book answer for sect. Ruderalia — the book side genuinely uses section names.
One side-effect worth noting either way: the slice export never shows this entity (slice = observed names only), which is why this never surfaced in the prototype queries — the micro slice has the same blind spot.
